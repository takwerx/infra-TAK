How to read: flat and near the bottom = the server is keeping up with fanout. A line that climbs and stays up = TAK is producing position updates faster than the network can send them (clients start lagging or dropping) — your fanout ceiling, even if CPU/RAM look fine. If the red dashed line is high but cyan is low, it's one slow client, not the whole server. Stalled connections (a queue that hasn't moved across samples — e.g. an idle Node-RED feed or a dropped client still holding a buffer) are excluded from this line and counted in the tile above, so leftover sockets don't masquerade as live backpressure.
External network throughput — TX / RX (bytes/s)
How to read: on a fanout server TX (out) should be much larger than RX (in) — one position comes in, a copy goes out to every other client. Watch whether TX grows in step with the client count (normal) or faster than it (you're approaching the network ceiling).
Connected clients
Live streaming clients right now. The baseline you compare everything else against — TX and the send-queue should scale with this.
JVM heap — used (MB)
TAK Server's Java memory. A sawtooth (climbs, then drops on garbage collection) is healthy. A line that climbs toward the top and never drops back = memory pressure.

Database maintenance (Authentik)▾

Authentik writes a record to authentik_tasks_task and authentik_tasks_tasklog on every background task. These tables are never automatically purged — after ~1 month of normal operation they can grow to 500–900 MB (88%+ of the Authentik DB), causing autovacuum lag and background writer CPU spikes. Guard Dog runs a weekly cleanup (Sunday 03:00) that deletes rows older than 30 days and runs VACUUM ANALYZE.
