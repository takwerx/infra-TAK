# infra-TAK platform reference

What infra-TAK depends on that it does not control: other products, package repositories, distros and cloud APIs. Each entry says what the outside thing does, where the official statement of it lives, and how sure we are.

Read the entry before you change code that talks to the thing. Platforms often fail vaguely on purpose (a generic login or certificate error can be a deliberate security choice), so read the contract before reasoning from the symptom. [ARCHITECTURE.md](ARCHITECTURE.md) covers our own code; this file covers everything outside it.

**How sure we are**

| Mark | Meaning |
|---|---|
| ✅ verified `<date>`, `<box>` | We reproduced or observed it on a real machine and wrote down which. |
| 👁 observed `<date>` | Seen in a field report or a test run. Not reproduced since. |
| 📖 documented | Stated by the official source. Not proven on one of our machines. |

When the official docs and what we saw disagree, keep both and say so. Never delete an observation. No passwords, tokens, customer data or private box addresses in this file.

## Ubuntu, apt and Ubuntu Pro

Official: [Ubuntu Pro client](https://documentation.ubuntu.com/pro-client/), [apt_preferences(5)](https://manpages.ubuntu.com/manpages/noble/man5/apt_preferences.5.html)

- **Stock Ubuntu 24.04 cloud images carry Ubuntu Pro pin files even when Pro is off.** `ubuntu-pro-client` writes `/etc/apt/preferences.d/ubuntu-pro-esm-apps` and `ubuntu-pro-esm-infra` (priority 510) whether or not the machine is attached. ✅ verified 2026-10-30, Azure Ubuntu 24.04.
  - Do not judge "is Pro on" from those files. Ask the client: `pro status --format json` and read `attached`. A `+esm` suffix on a version in apt output also means Pro is on. `_ubuntu_pro_security_covered()` in `app.py` does it this way and treats any doubt as "not covered".
- **A priority of 510 beats the default 500.** apt picks the highest-priority candidate before it looks at version numbers. On a box with Pro attached, an ESM copy of a package therefore beats a newer PGDG copy of the same package. 📖 apt_preferences(5).
- **PGDG's PostGIS and Ubuntu's ESM GDAL cannot be installed together.** The TAK Server `.deb` pulls PostGIS from PGDG, which links PGDG's own newer GDAL, GEOS and PROJ. With Pro's pin in play apt takes `gdal-data` from ESM and the install stops with `libgdal39 : Depends: gdal-data (>= …pgdg…) but …+esm1 is to be installed`. 👁 observed 2026-10-29 (GH #352); the ESM pin can be modelled without a Pro token in a fresh Ubuntu container with `Pin: release o=Ubuntu` at 510.
  - Our fix pins the GIS packages plus `postgresql-common`, `postgresql-client-common` and `libpq5` to `o=apt.postgresql.org` at 600. 600 is above ESM's 510 and below 1000, so nothing is ever downgraded. It lives in `_PGDG_GIS_PIN_BODY`.
  - A plain box is unaffected: PGDG already wins on version.
- `apt-cache pkgnames libgdal` is a prefix match. It also lists `-dbgsym` and `-dev` packages. Filter with `^libgdal\d+[a-z0-9]*$` when you want the runtime library.
- **One apt repository configured two ways breaks every apt command on the box.** If the same URL appears in two `sources.list.d` files with different `Signed-By` keyrings, apt normalises the URLs, sees a conflict and refuses to read any source. Use one filename and one keyring for PGDG everywhere, and skip adding it when the box already has it. 👁 observed (see the comment above `_PGDG_LIST` in `app.py`).
- The apt codename comes from `/etc/os-release`, not `lsb_release`. A minimal 24.04 image can lack `lsb_release`, and an empty codename writes `apt -pgdg main`, which apt rejects for every source. 👁 observed, v10.3.0.
- To model apt behaviour without a Pro token or a new VM, use a fresh `ubuntu` container and write the pin file by hand.

## ufw and fail2ban (Ubuntu firewall bans)

Official: [ufw(8)](https://manpages.ubuntu.com/manpages/jammy/man8/ufw.8.html), [fail2ban action.d/ufw.conf](https://github.com/fail2ban/fail2ban/blob/1.0.2/config/action.d/ufw.conf)

- **`ufw insert 1 reject from <IPv6>` always fails; `ufw prepend reject from <IPv6>` works.** ufw 0.36.1 (Ubuntu 22.04) and 0.36.2 (24.04) answer `ERROR: Invalid position '1'` for an IPv6 source at position 1, even with no other rule. The same command with an IPv4 source works. The stock fail2ban 1.0.2 ufw action already uses `add = prepend`; the stock 0.11.2 action (Ubuntu 22.04) still uses `insert <insertpos>`. So no IPv6 ban in an all-ports ufw jail became a firewall rule until `infratak-ufw` switched to `ufw prepend` (ops #1275). `ufw delete reject from <IPv6> to any` removes the rule; deleting one that is not there returns 0. ✅ verified 2026-11-25, Ubuntu 22.04 (ufw 0.36.1, fail2ban 0.11.2) and 24.04 (ufw 0.36.2, fail2ban 1.0.2) containers, and aws-arm (Ubuntu 22.04 ARM64, ufw 0.36.1, fail2ban 0.11.2).
- **fail2ban reads an action file only when it starts.** A reload leaves current bans on the action they were made with, so a changed action file reaches a box only after a stop and start. The console does that under the ufw lock (`_startup_f2b_ufw_lock_switch`). On aws-arm the first console start on the new code restarted fail2ban once; the second console start did not. ✅ verified 2026-11-25, aws-arm (ops #1275).
- In the numbered `ufw status`, a `(v6)` rule is numbered after all IPv4 rules, so a freshly prepended IPv6 ban shows at a high number (36 of 37 on aws-arm). It is still first among the IPv6 rules. 👁 observed 2026-11-25, aws-arm.

## PGDG (PostgreSQL package repositories)

Official: [apt](https://wiki.postgresql.org/wiki/Apt), [yum/dnf](https://www.postgresql.org/download/linux/redhat/)

- Debian family: `https://apt.postgresql.org/pub/repos/apt <codename>-pgdg main`, signed by the key at `postgresql.org/media/keys/ACCC4CF8.asc`.
- Rocky/RHEL: install `pgdg-redhat-repo-latest.noarch.rpm` for the right `EL-<major>-<arch>`. The repo paths use the **minor** release (`$releasever_minor`), and PGDG only publishes paths for current minors. On an old Rocky minor (9.3 was tried) `pgdg-common` answers 404 and the install fails. A current image works (9.8 tried). 👁 observed 2026-10-30. Rule for tests: use the newest Rocky 9 image, never an old pinned minor.
- The TAK Server 5.8 upgrade can leave the old PostgreSQL 15 cluster behind. infra-TAK offers to remove it (Guard Dog, v10.2.30). 👁 observed.

## Rocky / RHEL 9 (dnf)

Official: [dnf docs](https://dnf.readthedocs.io/), [RHEL 9 docs](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/9)

- Always go through `_pkg_install` / `_pkg_remove` and the firewall seams (`firewalld` here, `ufw` on Ubuntu). See [ARCHITECTURE.md](ARCHITECTURE.md), "The seams".
- **SELinux types from `container-selinux` do not exist until that package is installed.** On Rocky 9 the type `container_runtime_exec_t` (the docker client) comes from `container-selinux`, not from `selinux-policy-targeted`. A module that names it in `require { }` compiles with `checkmodule` and `semodule_package`, then fails at `semodule -i` with `Failed to resolve typeattributeset statement` until the package is there. `takwerx_console_confined` names it, so `start.sh` installs `container-selinux` before the module (Docker, which needs the package anyway, is installed later). ✅ verified 2026-11-24 in a `rockylinux:9` container (selinux-policy-targeted 38.1.86, checkpolicy 3.6): `seinfo -t container_runtime_exec_t` finds nothing in the base policy; the module fails to link; after `dnf install container-selinux` (2.250.0) the same `.pp` links. Also verified on a fresh-install Rocky 9 box: with the package first, the module installs and the console runs as `takwerx_console_t`. Official: [container-selinux](https://github.com/containers/container-selinux).
- The Rocky cloud image on Azure needs marketplace terms accepted by a person. For a throwaway Rocky 9 test, run the official `rockylinux/rockylinux:9` container instead. 👁 observed 2026-10-30.
- A born-non-root console cannot `sudo`; privileged work goes through the broker (`broker/`). Probing such a box as any other user, with the broker shims on `PATH`, answers "service inactive" or "file missing" when the truth is "wrong user".
- **A nosuid mount changes what systemd may start from it.** Rocky/RHEL 9 kernels have the policy capability `nnp_nosuid_transition` set (`/sys/fs/selinux/policy_capabilities/nnp_nosuid_transition` reads `1`). With it, a domain change at exec from a `nosuid` mount needs `allow init_t <domain>:process2 nosuid_transition;`. The broker makes the console's folders (`/opt/infratak`, `/home/takwerx`) `nosuid,nodev` (ops #645). A unit with `SELinuxContext=...takwerx_console_t` then dies with `203/EXEC`, `Failed to execute /opt/infratak/.venv/bin/gunicorn: Permission denied`, and `journalctl` shows setroubleshoot "SELinux is preventing /usr/lib/systemd/systemd from using the nosuid_transition access on a process". The rule is in `takwerx_console_confined` 2.2. ✅ verified 2026-11-24, nuc (Rocky 9.9) and a fresh-install Rocky 9 box (selinux-policy 38.1.86): module 2.1 + nosuid folders = console restart fails; module 2.2 + the same folders = starts and answers on 5001. Official: [SELinux Notebook](https://github.com/SELinuxProject/selinux-notebook), object class `process2`.
  - The **unconfined** unit (`SELinuxContext=...unconfined_service_t`) starts from the same nosuid folders with no extra rule. ✅ verified 2026-11-24, the same fresh-install box.
  - `ausearch -m avc` found no line for this denial on that box (auditd was active). Read the journal (setroubleshoot) instead.
- **The confined console may `readlink` another process's `/proc/<pid>/exe` but may not `lstat` it.** `takwerx_console_confined` gives `takwerx_console_t` `domain:lnk_file read` and no `getattr`. `os.readlink()` needs only `read`. `os.path.realpath()`, `os.lstat()`, `Path.resolve()` and `os.path.islink()` call `lstat` and each makes one denial, which setroubleshoot logs at priority err (`SELinux is preventing /usr/bin/python3.9 from getattr access on the lnk_file /proc/<pid>/exe`). The kernel already returns the resolved path from readlink, so use readlink alone. ✅ verified 2026-11-26, nuc (Rocky 9, SELinux Enforcing, console in `takwerx_console_t`): `os.path.realpath` in `_trusted_java_exe` made about 2.4 to 2.9 denials a minute (477 in 3 hours; 64 in the 27 minutes before the change, 14 in 4.8 minutes after going back to the old code); with `os.readlink` alone, 0 denials in 10.8 minutes and no other denial in that time. ops #1298. Official: [SELinux Notebook, object classes](https://github.com/SELinuxProject/selinux-notebook) (`lnk_file`: `getattr`, `read` are separate permissions).
  - `checkmodule -M -m -o X.mod X.te` fails with "Module name … is different than the output base filename" unless `X` is the module name written on the first line of the `.te`.

## TAK Server

Official: TAK Server Configuration Guide and release notes at [tak.gov](https://tak.gov) (account required); [TAK Product Center on GitHub](https://github.com/TAK-Product-Center/Server)

- Ports we rely on: 8089 (streaming, mutual TLS), 8443 (admin/API, mutual TLS), 8446 (certificate enrollment and the username/password web login). 📖
- **Usernames are pasted into an LDAP DN without escaping.** A user whose name contains `/` can log in but receives no groups. A name containing any of `\ , + " < > ;` cannot log in at all. No setting changes this; the user has to be renamed. 👁 observed 2026-10-30 (infra-TAK warns about these names). The vague failure is why this is easy to misread as an Authentik or LDAP bug.
- **CoreConfig `<ldap updateinterval>` is in milliseconds.** The Configuration Guide (5.7 and 5.8) says "Frequency (in milliseconds) at which the server refreshes group memberships from LDAP" and its example is `60000`. infra-TAK wrote `30` for a long time, which expired the cache on every check and sent every lookup live to LDAP. It now writes `TAK_LDAP_UPDATE_INTERVAL_MS = '30000'`. 📖 Configuration Guide 5.7/5.8. ⚠ Disagreement: older private notes describe the value as "30 seconds"; the guide and the code comment are the authority.
- **Channels come from a group cache, not a live lookup.** Login does a live LDAP bind; the channel list comes from the cached user-to-groups map. A user created seconds ago can connect and see no channels until the cache refreshes. Only LDAP groups whose `cn` starts with `tak_` become channels. 👁 observed.
- **A failed LDAP group lookup for a certificate login silently means "no groups".** In TAK Server 5.8, `X509Authenticator` calls `LdapAuthenticator.getGroupInfoBySearch`, which catches every LDAP error, logs it only at DEBUG and returns an empty map. Nothing shows in the normal logs. ✅ verified 2026-10-30, TAK Server 5.8 jar on an Ubuntu dev box (decompiled).
- **After Authentik's server and worker restart and the LDAP outpost is recreated under a running TAK Server, the 8443 side can give fresh certificate logins no groups for minutes.** Measured 75 s to about 5.5 min on a busy box (CloudTAK, Node-RED, ATAK clients connected); it recovers by itself, no TAK restart needed. Connected 8089 clients keep their groups. During the gap TAK sends no LDAP lookup at all for the affected user (packet capture on the outpost port) while it keeps looking up others, and no thread is waiting in LDAP code. A plain outpost recreate, without the server/worker restart, recovered in about 12 s. ✅ verified 2026-10-30, Ubuntu dev box, TAK Server 5.8, Authentik 2026.8.5. Not known: where TAK holds the empty result; it is longer than `updateinterval` (30 s) and was not found in the decompiled classes.
- `x509useGroupCacheRequiresExtKeyUsage="false"` in `<auth>` lets certificates made by `makeCert.sh` (no extended key usage) use channels. 📖 notes, carried from the field.
- Mission API quirks (📖 from our notes, not re-proven): `PUT /Marti/api/missions/{name}/subscription?uid=X` assigns `defaultRole` even to an admin, so follow it with a role `PUT`. `PUT .../contents` needs the UID in the CoT cache first. `PUT .../role` needs the `group` to match the mission's group or TAK answers `FORBIDDEN: Illegal attempt to change Mission groups!`.
- **`POST /Marti/api/missions/{name}/feed` (add a data feed to a mission) always answers HTTP 500 on TAK Server 5.8.** TAK's `MissionApi.java` maps two `POST` handlers, `addFeed` and `addFeedByGuid`, to the same pattern `/missions/{x:.+}/feed`, so Spring answers `Ambiguous handler methods mapped` for every call. `/missions/guid/<guid>/feed` is a 404. ✅ verified 2026-11-13, test6 (TAK Server 5.8-RELEASE84); cause read in the public source (5.7-RELEASE-14). Reported upstream: [TAK-Product-Center/Server#76](https://github.com/TAK-Product-Center/Server/issues/76). infra-TAK never calls this endpoint (Node-RED uses a mission's `changes`, `role` and `contents` paths). Also: `DELETE /Marti/api/datafeeds/<uuid>` answers 400 when the uuid has a hyphen; delete by feed name instead. ✅ verified 2026-11-13, test6.
- **A new TAK Server 5.8 has no CoT retention at all.** `/opt/tak/conf/retention/retention-policy.yml` ships with `dataRetentionMap: cot: null`, and `retention-service.yml` ships with `cronExpression: "-"` (the retention job never runs). On a box where an operator set a policy in the Web Admin, the file reads `cot: 86400` (seconds) and the service file reads `cronExpression: 0 59 * * * *` (every hour at minute 59). infra-TAK reads these files and never writes them. ✅ verified 2026-11-16, Rocky 9 box with no policy and two Ubuntu boxes with `cot: 86400`, TAK Server 5.8.
- **TAK's hourly retention job deletes by `servertime`, which is when the server received the row, not when the row became deletable.** A CoT row that belongs to a mission (`mission_uid`) is kept. When it stops belonging to one, it can be days old at that moment and is deleted by the next hourly run. A check that looks once, between those two moments, sees an old row that is not stuck. ✅ verified 2026-11-16, Ubuntu 22.04 split-database box and Ubuntu 24.04 box (retention logged 24 runs a day, 14,000 to 18,000 rows a day); ⚠ not proven: what made the rows deletable.
- A user named `webadmin` in the flat-file `UserAuthenticationFile.xml` shadows an LDAP user of the same name. Do not create one in Authentik.
- A Java heap that is too small can show up as HTTP 500 on CloudTAK sign-in. 👁 observed.
- **The 5.8 hardened Docker bundle pins its Java to one exact Temurin build.** `docker/Dockerfile.hardened-takserver` starts with `ARG BASE_DEPLOY_TAG=17.0.19_10-jdk-ubi10-minimal` (base `docker.io/library/eclipse-temurin`). `docker build --pull` refreshes a tag that moves, but never an exact pin, so an image built from RELEASE-75 runs Java 17.0.19 (April 2026) however often it is rebuilt. infra-TAK bumps that one line (`_patch_tak_hardened_java_pin`). ✅ verified 2026-11-19 on nuc (Rocky 9, Docker): the shipped Dockerfile built with `--pull` ran Temurin 17.0.19+10; with the pin moved it ran 17.0.21+9. Docker Hub's `last_updated` for a Temurin tag is its latest rebuild, not its release date; [Adoptium's release list](https://api.adoptium.net/v3/assets/feature_releases/17/ga?vendor=eclipse&os=linux&architecture=x64&image_type=jdk) has the real dates (17.0.21+9: 2026-10-22; 17.0.21.1+2: 2026-11-18, Docker Hub tag `17.0.21.1_2-jdk-ubi10-minimal` pushed 2026-11-20). ⚠ That 17.0.21.1_2 `ubi10-minimal` manifest lists amd64, ppc64le and s390x only, NO arm64 (Docker Hub API, 2026-11-22), while `17.0.21_9-jdk-ubi10-minimal` and the shipped `17.0.19_10` do have arm64. So the pin is chosen by the host's architecture (`_temurin17_fixed_tag()`): amd64 gets 17.0.21.1_2, arm64 stays on 17.0.21_9 until Docker Hub adds arm64 to the newer tag.

## Authentik and the LDAP outpost

Official: [docs.goauthentik.io](https://docs.goauthentik.io/), [LDAP provider](https://docs.goauthentik.io/add-secure-apps/providers/ldap/), [configuration](https://docs.goauthentik.io/install-config/configuration/)

- Verify config with Authentik's own command, never by the fact that the process started: `ak dump_config` inside the server container. Environment variables use a **double underscore** between sections (`AUTHENTIK_WEB__WORKERS`, not `AUTHENTIK_WEB_WORKERS`). The single-underscore form was silently ignored for five releases. 📖 configuration docs; 👁 observed April 2026.
- **A new Authentik user is missing from LDAP search for about 2–4 minutes.** Wait. Do not restart `authentik-ldap-1` to "fix" it. 👁 observed 2026-10-30.
- The outpost caches the directory (`bind_mode` and `search_mode` cached), so a group change in Authentik reaches TAK Server after the cache time plus TAK's own refresh. 📖
- **The LDAP outpost (`bind_mode: cached`) remembers a refused sign-in with no end date, so a user stays refused after the reason is gone.** It keeps every bind result per bind DN and password, refusals too, for as long as the DN's stored session lives. A DN with no good sign-in in the last hour has a session with no expiry, and the cache library (ttlcache) keeps an entry with a ttl of 0 or less for ever. Two cases: an account disabled and enabled again (the right password stays refused), and a password set to a value that was tried before. Authentik's own flow accepts the password the whole time. Only a new cache clears it. An outpost restart does. So does saving the LDAP provider with `bind_mode` direct and then cached again: the outpost keeps the old cache when the old binder is a session binder and builds a new one when it is not. The log line `initialized direct binder` appears once for each new direct binder and for each new cache. A restart is the worse fix here (the 8443 side can lose LDAP groups, see above). 📖 source at `version/2026.8.6`: `internal/outpost/ldap/bind/memory/memory.go`, `bind/direct/bind.go`, ttlcache `item.go`. ✅ verified 2026-11-24, nuc, Authentik 2026.8.6: both cases stuck on the old code and fixed by the direct-then-cached save in 12 to 25 s, with TAK Server, the outpost and Node-RED not restarted (ops #1185, #1154). Not checked: other Authentik versions.
- TAK Server binds as the service account `adm_ldapservice`. Besides that service account, the `tak_ROLE_ADMIN` group and the `webadmin` user are the only group and user infra-TAK creates itself. Every other `tak_*` group comes from TAK Portal.
- After restarting `authentik-worker`, blueprints have to re-apply before LDAP queries work.
- **Authentik does not limit the characters in a username or a group name.** Its API (`POST /api/v3/core/users/`, `POST /api/v3/core/groups/`) stored names with spaces, quotes, `<`, `>` and `&` exactly as sent. Treat every name that comes from Authentik as free text: escape it for the place it goes (a page, a shell command, an LDAP filter). ✅ verified 2026-11-17, test6, Authentik 2026.8.5 (ops #827).
- **The proxy outpost picks which application to check from the request host, and it reads `X-Forwarded-Host` before `Host`.** Sign-in sessions are per application (one cookie per application). So whatever sits in front of the outpost must set `X-Forwarded-Host` itself (see Caddy below). 📖 Authentik source, tag `version/2026.8.5`: `lookupApp` in `internal/outpost/proxyv2/handlers.go` calls `web.GetHost`.
- **For a person's exact groups, ask the API. Do not split the proxy header.** The proxy outpost gives the app behind it the groups as one header, `X-authentik-groups`, with the names joined by `|` (📖 [proxy provider](https://docs.goauthentik.io/add-secure-apps/providers/proxy/)). A group name is free text and can hold `|`, `;` or `,` (the groups API stored all three, HTTP 201), so a split of the header does not give back the names that went in. The exact list is `groups_obj` from `GET /api/v3/core/users/?username=NAME&include_groups=true`: one entry per group. Compare the returned `username` too, because Authentik ignores a filter it does not know and then returns every user. The header and `groups_obj` come from the same list, the person's own groups (📖 source at `version/2026.8.5`: `blueprints/system/providers-oauth2.yaml` profile scope, `authentik/core/api/users.py`). ✅ verified 2026-11-22, fresh-install box (Ubuntu 22.04), Authentik 2026.8.5: roles taken from the API list matched the header for normal names (ops #1082).
- **Authentik does not require a user's email to be unique.** Two users created through the API with the same address both got HTTP 201. So several infra-TAK admin accounts can share one operator address. ✅ verified 2026-11-23, fresh-install box (Ubuntu 22.04), Authentik 2026.8.x (ops #1169). **TAK Portal mails the `email` of every member of its required group (`authentik Admins`) when a user asks for access** (📖 read in TAK Portal's `userRequests.service.js` by the reporter of infra-TAK #687; mail delivery itself not re-run here). An address on the TAK domain has no MX, so those mails bounce; new infra-TAK admin accounts take the first Guard Dog alert address (`_ak_admin_account_email`).
- Two things at once on one box can starve it. A first-time Authentik deploy next to a TAK Server, Node-RED and MediaMTX deploy has produced `127.0.0.1:9090: connection refused` (502) from Caddy. Space deploys out. 👁 observed.

## TAK Portal

Official: [ValleyTacticalSolutions/TAK-Portal](https://github.com/ValleyTacticalSolutions/TAK-Portal) (our `TAKPORTAL_REPO`)

- Its `settings.json` belongs to the operator. infra-TAK writes only the keys in `TAKPORTAL_AUTHORITATIVE_KEYS` (`AUTHENTIK_URL`, `AUTHENTIK_TOKEN`, and the email transport keys while Email Relay is configured) and seeds the rest once. One writer: `_takportal_merged_settings_json()` / `_takportal_write_settings_json()`. Never infer ownership from a value. See the hard stop in the project rules.
- **"Deploy To Caddy" can report failure when Caddy reloaded fine.** TAK Portal runs `bash -lc 'set -euo pipefail; …; exit 0'` over SSH (`deployPluginCaddy`, `services/cloudtakMarketplace.service.js`). A login shell reads `~/.bash_logout` on exit and **errexit is still on there**: Ubuntu's stock file ends with `[ -x /usr/bin/clear_console ] && /usr/bin/clear_console -q`, which fails with no terminal, so the whole command exits 1 after the helper had already written and reloaded Caddy, and the Portal shows the helper's own success text as the error. ✅ verified 2026-11-17 on Ubuntu 22.04 with a real sshd (bash 5.1): stock file rc 1; stock file plus `true` at the end rc 1 (errexit stops the file at the failing line, so the first idea, appending `true`, does not work); `set +e` as the first line rc 0; no file rc 0. Without `set -e` the same file does not change the exit code (that is why a plain `bash -lc 'exit 0'` probe shows rc 0). infra-TAK puts a marked `set +e` at the top of the console user's existing `~/.bash_logout` (`_takportal_harden_logout_file`, ops #879). An earlier note here said the fix belonged in TAK Portal and gave a different cause; 👁 first observed 2026-10-30. A change in TAK Portal (drop `set -e` for the login shell) would also fix it.
- Upstream versions can lie: the 2.0.15 tag shipped a `package.json` whose `version` still said 2.0.14 (the real number was in `beta-version`). Read the field the release actually bumps. 👁 observed 2026-10-21 (GH #214).
- **Users get a TAK Portal release only after it passes our Marketplace gate (ops #1042).** TAK Portal's maintainers can break the Marketplace with any release and we do not control them: 2.0.38 refused the `// @ts-nocheck` that the d4h plugin ships in its own route files, so every Marketplace install failed on a box with that plugin (ops #1037, TAK-Portal#144; 2.0.39 fixed it 40 minutes after the report). infra-TAK no longer reads GitHub `releases/latest` for TAK Portal. Deploy, the Update button, the update badge and Guard Dog's "Update pending" read one signed file, `takportal-verified.json` (+ `.sig`) in `takwerx/infratak-etl-catalog`: it names the tag, the commit the tag must point to, a held list, `"kind": "takportal-verified"` (the ETL catalog is signed with the same key, so a file of another kind is refused) and an `expires` date (UTC, YYYY-MM-DD: a fetched file past its date is refused so an old signed file cannot be replayed to a new box; a file a box already accepted keeps working, so a missed renewal never pushes boxes back to the floor). Same offline Ed25519 key as the ETL catalog (`modules/etlrunner/catalog_signing.pub`); the serial must never go down; with no valid file a deploy uses `TAKPORTAL_REF_FALLBACK` and the badge stays silent. TAK Portal's own `[update] X -> Y available` log line is not read: it names TAK Portal's newest release. ## MediaMTX

Official: [bluenviron/mediamtx](https://github.com/bluenviron/mediamtx), [mediamtx.org](https://mediamtx.org/)

- We run bluenviron's binary and our own web editor ([takwerx/mediamtx-installer](https://github.com/takwerx/mediamtx-installer)) as separate services. After the editor is patched, restart `mediamtx-webeditor` as well as MediaMTX itself. 👁 observed.

- A MediaMTX unit written for Caddy's group fails on a box without Caddy with `216/GROUP` and crash-loops. 👁 observed (v10.3.3).
- **The HLS playlist keeps only `hlsSegmentCount` segments, and MediaMTX drops the oldest listed segment about one segment after it listed it.** hls.js starts `liveSyncDurationCount` segments back from the end of the playlist, so a count at or above `hlsSegmentCount` starts at that oldest segment; on a slow link the request arrives after the drop, answers 404, and no video starts. A segment is as long as the source's keyframe interval, not `hlsSegmentDuration` (MediaMTX cuts only on a keyframe): with 1-second keyframes and `hlsSegmentCount: 3` the playlist holds 3 one-second segments. Keep the player's `liveSyncDurationCount` at most `hlsSegmentCount - 1`. ✅ verified 2026-11-17, aws-arm and a local run (MediaMTX v1.20.0, hls.js 1.6.16, Chrome, 1-second keyframes, `hlsSegmentCount: 3`, `hlsSegmentDuration: 500ms`): with `liveSyncDurationCount` 4, 19 of 32 stream-site starts on the box played, and 10 to 11 of 16 locally with 0.4 s added to each answer; with 2, 32 of 32 and 16 of 16. With no added delay all 8 played, so it only shows on a slow link. A player that calls `startLoad()` on a non-fatal network error (CloudTAK's `VideoPlayer.vue` does) recovered 16 of 16 at `liveSyncDurationCount: 3`; one without it did 10 of 16. 📖 MediaMTX's own `mediamtx.yml` (v1.20.0) says `hlsSegmentCount` is the "number of HLS segments to keep on the server" and that the segment duration follows the interval between IDR frames. It does not say when a listed segment is dropped, so that timing is our measurement only.
- **MediaMTX loads a changed `mediamtx.yml` by itself, and a changed `hlsAddress` moves only the HLS listener.** No restart is needed and the publishers stay. 📖 [Configuration](https://mediamtx.org/docs/usage/configuration): "You can edit the configuration file when the server is running (hot reloading). Changes are detected and applied without disconnecting existing clients, whenever it's possible." The page does not say which settings need more than that, so check the listener after a change (`ss -ltn`) and restart only when it did not move. ✅ verified 2026-11-25, MediaMTX 1.21.4 on a throwaway Ubuntu 22.04 host: after `hlsAddress` changed from every interface to `127.0.0.1`, the HLS listener moved in about 1 second in the same process and the RTSP listener stayed. The log says `reloading configuration (file changed)`, `[HLS] closing`, `[HLS] started with listener on 127.0.0.1`. The change back works the same way. Through the console, on an Ubuntu 22.04 host and a Rocky 9 host (SELinux Enforcing), the listener moved with the same pid and 0 restarts, and on the Ubuntu host both test publishers kept running.

## Federation Hub

Official: the Federation Hub Configuration Guide (5.8, in `/opt/tak/docs/` of a TAK Server install and on [tak.gov](https://tak.gov)); the TAK documentation site ("Fedhub Docs", also inside a TAK Server install under `/Marti/documentation/`). Checked against `takserver-fed-hub_5.8-RELEASE104_all.deb` on Ubuntu 22.04.

- **The hub's web server refuses more than 8,192 bytes of request headers: HTTP 431.** ✅ verified 2026-11-24, fresh Ubuntu 22.04 box (hub on its own host): 7,900 bytes of Cookie header answered 404, 8,100 answered 431, straight to port 8080 and through Caddy. Anything in front of the hub that adds a header per user can break it: Authentik's `X-Authentik-Groups` grows with every group (10,638 bytes for 200 groups). infra-TAK therefore sends the hub no `X-Authentik-*` header.
- **The hub reads no Authentik header.** ✅ verified 2026-11-24: no class in the hub's UI, broker, policy, manager or shared jars names `X-Authentik` or `X-Forwarded-User`. Its own login is OIDC (the `keycloak*` keys of `federation-hub-ui.yml`, which infra-TAK points at Authentik) or a client certificate listed in `authorized_users.yml`. Caddy's `forward_auth` only decides who may open the page.
- Ports: 8080 (web, plain HTTP, what Caddy proxies to), 9100 (web, HTTPS), 9101 (federation v1), 9102 (federation v2), 9103 (token auth, only when configured). ✅ verified 2026-11-24: 8080, 9100, 9101, 9102 listen after a deploy.
- **The hub makes its own certificate authority at install (`FEDHUB-ROOT-CA`, `FEDHUB-INT-CA`).** Each TAK Server must trust the hub's `ca.pem` (TAK page "Upload federate certificate", or `POST /Marti/api/federatecertificates`, multipart part `file`), and the hub must trust each server's CA (hub page "CA Manager", or `POST /api/addNewGroupCa` on the hub's admin port with the parts `file` and `nickname`). ✅ verified 2026-11-24, two TAK Servers 5.8 and one hub.
- **The hub finds a server by the CA chain it presents, and the chain gives two identities** (the intermediate and the root, each as `<issuer DN>-<SHA-256 of the certificate>`). Uploading only `ca.pem` (a bundle of both certificates) stores the intermediate. ✅ verified 2026-11-24: with the bundle and the single root of each server (four CA entries and a policy that lets all four talk), both servers connected. Whether the two bundle entries alone are enough is 👁 not proven (the connections that existed when we tried it stayed up, so the test showed nothing). Two servers whose CAs have the same subject name but different keys work, because the hub keys on the hash. ✅ verified 2026-11-24.
- **A policy only reaches the broker through the "core" save.** On the hub's admin API, `POST /api/saveFederationPolicy` alone left both servers refused with `Permission Denied. Federate/CA Group not found in the policy graph` even though the policy listed their CAs and `activateFederationPolicy/<name>` answered 200. Adding `POST /api/saveFederationCorePolicy` with the same JSON before activating made both connect. ✅ verified 2026-11-24. Order that worked: `addNewGroupCa` for each CA, `saveFederationPolicy`, `saveFederationCorePolicy`, `POST /api/activateFederationPolicy/<name>`. The admin API wants the admin client certificate (`webadmin-fed`). Entity type names in the policy JSON are `FederationGroup`, `FederationTokenGroup` and `FederationOutgoing`.

## Caddy

Official: [caddyserver.com/docs](https://caddyserver.com/docs/), [forward_auth](https://caddyserver.com/docs/caddyfile/directives/forward_auth), [reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)

- Reload (`systemctl reload caddy`) to apply a rewritten Caddyfile without dropping connections. Check a file with `caddy adapt` before reloading. 📖
- `forward_auth` is how protected sites ask Authentik first. Our notes say it must come before `reverse_proxy` in a site block; confirm the ordering against the Caddy directive-order table before relying on it. Not re-proven here.
- **`forward_auth` is a `reverse_proxy` shortcut and takes its subdirectives** (`trusted_proxies`, `header_up`). Caddy writes `X-Forwarded-For`, `X-Forwarded-Proto` and `X-Forwarded-Host` on the request to the auth server itself. Without `trusted_proxies` it replaces whatever the client sent. With `trusted_proxies <ranges>` it keeps the `-Proto` and `-Host` a client in those ranges sent, and appends to its `-For`. A `header_up X-Forwarded-Host …` line wins over both. 📖 [reverse_proxy, "Defaults" and `trusted_proxies`](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#defaults). ✅ verified 2026-11-22, a local run of Caddy 2.7.6 and 2.11.4 with a stand-in auth server and a loopback client: all three cases seen on both versions.
  - `X-Forwarded-Method` and `X-Forwarded-Uri` are always set by `forward_auth` itself.
  - The Authentik outpost picks the application it checks from `X-Forwarded-Host` (see Authentik below), so our blocks have no `trusted_proxies` line and set `-Host` and `-Proto` with `header_up` from `{http.request.hostport}` and `{http.request.scheme}`. `{http.request.hostport}` is what Caddy sends by default: the port is there only when the client's `Host` has one (a moved HTTPS port). One helper writes every block: `_caddy_forward_auth_lines` in `app.py`.
  - The `trusted_proxies private_ranges` line in Authentik's Caddy example is marked optional there. 📖 [Authentik, forward auth with Caddy](https://docs.goauthentik.io/add-secure-apps/providers/proxy/server_caddy/)
- **After a passed sign-in check, a site can compare which application the answer is for.** The proxy outpost names it in the answer header `X-authentik-meta-app` ("Slug of the authentik application"). 📖 [Authentik, proxy provider, "Headers sent to upstream applications"](https://docs.goauthentik.io/add-secure-apps/providers/proxy/). ✅ verified 2026-11-23 on a fresh-install box, Authentik 2026.8.5: a passed check for the TAK Portal site answered with `tak-portal`; a refused check (302) had no such header.
  - In a `route`, our blocks remove the client's own copy (`request_header -X-Authentik-Meta-App`), copy the answer's with `copy_headers`, then refuse with `@ak_other_app not header X-Authentik-Meta-App <slug>` and `respond @ak_other_app … 403`. The `header` matcher is an exact match when the value has no `*`. 📖 [Caddy, request matchers, `header` and `not`](https://caddyserver.com/docs/caddyfile/matchers#header). The Caddy pages do not say what a value match does when the header is absent, or what `copy_headers` does when the answer lacks a header. ✅ verified 2026-11-23, a local run of Caddy 2.7.6 and 2.11.4 with a stand-in auth server: an answer for another application, an answer with no application header, and a client that sends the header itself all get 403; another letter case and a longer name that starts the same get 403; the right application passes. Caddy 2.7.6 hands the asked headers on empty when the answer lacks them; 2.11.4 leaves them out.
  - **These lines must sit in a `route`.** In a `handle` Caddy sorts directives, so both `request_header` lines run after `forward_auth` and before `respond`: the copied header is gone and every request gets 403. ✅ verified 2026-11-23, a local run of Caddy 2.7.6 and 2.11.4: the right application got 403 in a `handle`. The Federation Hub site keeps its check in a `handle`, so it gets no compare.
  - No compare for a provider with unauthenticated paths (`skip_path_regex`) or for a host that two providers name. Not tested on a box: we expect the outpost to pass an unauthenticated path with no application named, and the compare would refuse it.
  - The slug of each site comes from Authentik's proxy provider list (`external_host` and `assigned_application_slug` of each `forward_single` provider, `GET /api/v3/providers/proxy/`). It is kept in `.config/forward_auth_apps.json`. A site that is not in that list gets no compare. The group header is not used for this: a group name can hold its separator.
- **For an `https://` upstream Caddy sends the upstream's address as `Host`, not the site's name (since v2.11.0).** An app behind it that builds links or checks its name from `Host` then sees an address. `header_up Host {hostport}` keeps the name the client asked for. When the upstream is an address, `tls_server_name <name>` in `transport http` tells Caddy which name the certificate must carry. 📖 [reverse_proxy, HTTPS](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#https): "Since Caddy v2.11.0, this is done automatically", and "If you wish to opt out of this behavior, you can set the `Host` header to its original value"; `tls_server_name`: "if the upstream address is an IP address, then you would need to configure this to the hostname being served by the upstream". The page does not say if the automatic value holds the port. ✅ verified 2026-11-25, Caddy 2.11.9 on a throwaway Ubuntu 22.04 console box with the MediaMTX web editor on a second box (Ubuntu 22.04 and Rocky 9): with `reverse_proxy https://<address>:5080`, `header_up Host {hostport}` and `tls_server_name <stream name>`, six users signed in through Authentik, landed on the stream site and played video through the editor. Not tested: the same block without the `header_up` line.
- **On Rocky/RHEL 9 Caddy runs as `httpd_t` and its own log roll needs rights the stock SELinux policy does not give.** `/var/log/caddy` is `httpd_log_t`; the COPR rpm labels the binary `httpd_exec_t`. With the stock policy `httpd_t` may create, write and append to a log it has but not rename or delete one. At `roll_size` Caddy's roll fails with `write error: ... can't rename log file ... permission denied` in its journal and `SELinux is preventing /usr/bin/caddy from remove_name access on the directory` from setroubleshoot; from then on every access line is dropped, so a log such as `takportal-access.log` (read by the TAK Portal fail2ban jail) stops growing for good. Ubuntu has no SELinux and rolls fine. ✅ verified 2026-11-26, nuc (Rocky 9.8, log stuck at 10,485,194 bytes since Sep 10, 3 requests gave 3 errors and 3 denials) and a fresh Rocky 9.9 box (same, then `takwerx_console` 1.1 let the roll, the gzip of the old file and the delete of the oldest roll all work, no denial). Official: [Caddy `log` `output file`](https://caddyserver.com/docs/caddyfile/directives/log#file), [Fedora/RHEL SELinux, `httpd_log_t`](https://access.redhat.com/documentation/en-us/red_hat_enterprise_linux/9/html/using_selinux/index).
  - What the stock policy has for `httpd_t` on `httpd_log_t` (`sesearch -A -s httpd_t -t httpd_log_t -c dir|file`, Rocky 9.9): dir `add_name create ioctl lock read setattr write`; file `create open read setattr` and, through `logfile`, `append getattr ioctl lock`. Missing: dir `remove_name`, file `write rename unlink`. Our rule is in `selinux/takwerx_console.te` (1.1).
  - **The denial can be hidden:** a box with the default `dontaudit` rules shows only the Caddy journal line, not an AVC; `semodule -DB` makes the denial show (nuc has it). The failing roll itself needs no audit to be real.
  - **A test Caddy site on a stock port fails to start on RHEL:** `httpd_t` may bind only the `http_port_t` ports (80, 81, 443, 488, 8008, 8009, 8443, 9000). Port 8099 gave `listen tcp :8099: bind: permission denied` and an AVC `name_bind`. Use 8008 or 8009 for test sites. ✅ verified 2026-11-26, Rocky 9.9.
  - A root-owned copy of the broker (nuc) installs a policy module only from a commit on `main`, `dev` or a release tag, so a branch's `.te` cannot be tried there; use a fresh-install Rocky box (the broker runs from `/opt/infratak`). ✅ verified 2026-11-26.

Official: [nodered.org/docs](https://nodered.org/docs)

- Function nodes cannot `require()` by default; declare modules in the node's `libs`.

## Reboots: what starts what, and in which order

Official: [Docker restart policies](https://docs.docker.com/engine/containers/start-containers-automatically/), [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)

- **`restart: unless-stopped` does not restart a container that was stopped on purpose before the reboot or the daemon restart, and `docker stop` counts as on purpose.** Guard Dog's boot sequencer stops Authentik, TAK Portal, CloudTAK and Node-RED (and MediaMTX) before TAK starts, so after a reboot only `tak-post-start.service` brings them back. 📖 documented (Docker); 👁 observed 2026-11-02 (ops #438: TAK Portal and CloudTAK stayed stopped after a 24.04 reboot while TAK, Authentik and Caddy ran).
- **`docker compose` `depends_on` is not honoured when dockerd restarts containers after a reboot.** dockerd starts them all at once, so the LDAP outpost can start before the Authentik server has published its providers and bind without resolving groups. 👁 observed 2026-08-31 (GH #64).
- **`tak-post-start.service` is one shot with `TimeoutStartSec=1200`, and its own waits add up to more than that** (Authentik healthy up to 300 s, LDAP group probe up to 120 s plus a 30 s recreate, TAK 8089 up to 900 s, TAK API up to 300 s, then the CloudTAK, Node-RED and MediaMTX staggers). On a slow boot systemd kills it before it has started the last modules, and nothing starts them again. 📖 read from the unit and the script, not yet reproduced on a box. The console's once-per-boot check (ops #1017) starts what is still stopped 10 to 21 minutes after boot.
- **Boot timings seen.** TAK Server opens 8089 about 110 to 170 s after start, and its API a few seconds to half a minute later. The Authentik LDAP outpost can take about 100 s after its own start before it resolves groups, so a bind probe in the first two minutes is not proof of anything. 👁 observed 2026-08-22 and 2026-11-20 (test6, test12, a field box).
- **A unit that is `activating` is not down.** `systemctl is-active` says `activating` while a unit starts; judge it only after the start has finished. 📖 documented (systemd).
- **A host can answer ping and refuse every TCP port after a reboot.** test6 (Ubuntu 24.04, VPS) did so for 25+ minutes after a real reboot on 2026-11-20 while test12 on the same code came back. Cause not yet known. 👁 observed 2026-11-20 (ops #1017); open question.

### Start-order map (ops #1017, read from the units and scripts of a full-module box, 2026-11-20)

"Enforced" = a unit dependency, a compose `service_healthy` wait or a health wait in code. "Timer-only" = nothing orders it; a per-minute Guard Dog timer or restart policy heals it later. "Nothing" = no order and no heal.

| Service | Needs first | Where the order is kept today | Mark |
|---|---|---|---|
| Docker | network-online, containerd, docker.socket, time-set | `docker.service` `After=`/`Requires=`, `Restart=always` | enforced |
| PostgreSQL (TAK) | disk, network | `takserver.service` `After=postgresql*.service`; Guard Dog `takdbguard` per minute | enforced (TAK side); heal timer-only |
| TAK Server | PostgreSQL, network | `After=postgresql*.service`, `soft-start.conf`; `tak-boot-sequencer.sh` (ExecStartPre) stops the heavy modules first so TAK gets the CPU | enforced |
| Authentik DB, Redis, pgbouncer | Docker | compose `depends_on: service_healthy` inside the stack; dockerd ignores `depends_on` after a reboot (GH #64) | timer-only after reboot (post-start + `takauthentikguard`) |
| Authentik server, worker | Authentik DB, pgbouncer, Docker | sequencer stops them, `tak-post-start` starts them after TAK answers; `takauthentikguard` per minute | enforced (post-start), heal timer-only |
| LDAP outpost | Authentik server answering | `tak-post-start` waits for it ("resolving groups"); the console boot heal waits for Authentik and (since 06c007e) for the outpost to listen | enforced |
| TAK clients with groups | LDAP outpost, TAK API | `tak-client-gate` holds 8089 until the API answers; #1015 stuck-phones check | enforced |
| TAK Portal | TAK Server, Authentik | `tak-post-start` starts it after the session recycle; `taktakportalguard` per minute | enforced + timer |
| CloudTAK (8 containers) | TAK Server, its own PostGIS | `tak-post-start`, 30 s stagger after TAK Portal; `takcloudtakguard` per minute | enforced + timer |
| Node-RED | TAK Server | `tak-post-start`, 30 s stagger; `taknoderedguard` per minute | enforced + timer |
| MediaMTX, web editor | network (editor: MediaMTX) | `tak-post-start` starts it last; `takmediamtxguard`; unit `Restart=always` | enforced + timer |
| Caddy | network-online, DNS for certificate renewals | `After=network-online.target`, `Requires=`; certificates are kept on disk; `Restart=on-failure` | enforced |
| Console and broker | network-online | `After=network-online.target`, `Restart=always`; boot heals wait for Authentik; ops #1017 boot check at 10 min | enforced; heal added |
| Guard Dog timers | none | systemd timers, per minute to daily | timer-only (by design) |
| fail2ban, tak-health | network, TAK (health) | unit `After=`, `Restart=` | enforced |
| Any module stopped by the sequencer and not started by `tak-post-start` | | ops #1017 boot check (10+ min after boot, 2 repair rounds, plain-words email) | added in PR 622 |

Gaps this map shows (not yet fixed here): the 30 s gaps in `tak-post-start` put the full stack at about 4.5 to 5.5 minutes on a small cloud box (a design choice: they keep CloudTAK and Node-RED from reaching TAK together); a clock that is wrong at boot and a full disk at boot have no own check.

## Shell scripts and systemd units that are rewritten while they run

Official: [bash manual, shell scripts](https://www.gnu.org/software/bash/manual/html_node/Shell-Scripts.html), [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)

- **bash reads a script file as it runs, not all at once.** If the file is rewritten in place (open with truncate, then write), a running script carries on from its old byte offset in the new content and ends with a syntax error or a random command, exit 2. Writing a temp file in the same directory and renaming it over the old one is safe: the running script keeps the old file. The console does this for `/opt/tak-guarddog/` and `/etc/systemd/system/` (ops #666). ✅ verified 2026-11-11, `tak-post-start.service` on an Ubuntu 22.04 dev box: console restarted while the unit ran, in-place rewrite gave `Result=exit-code`, `ExecMainStatus=2` and no "Boot sequence complete"; with the rename write the unit ended `Result=success`.
- **A rename is not always right.** It breaks a single-file bind mount into a container (the container keeps the old file) and a log file that a running process holds open. Files like those stay written in place. ⚠ not re-tested for ops #666; the bind-mount case was seen with the NetBird CA bundle (ops #433).

## Virtual machine CPU level (TAK Portal and CloudTAK)

Official: [sharp, installation](https://sharp.pixelplumbing.com/install) (the image library both products load)

- **TAK Portal and CloudTAK need an x86-64-v2 CPU or newer on Intel/AMD boxes.** Both use the `sharp` module, whose prebuilt Linux x64 binaries need those CPU features.   - The usual cause is a VM set to a generic or "basic" CPU type (TrueNAS, KVM and Proxmox defaults), which hides the features the real CPU has. The fix is in the hypervisor: set the VM's CPU mode to host passthrough (or host model). No reinstall; the reporter confirmed it fixed both. 👁 observed 2026-10-31.
  - The flags the v2 level adds that we check: `popcnt`, `sse4_1`, `sse4_2` (in `/proc/cpuinfo`). ARM boxes are not affected.
  - Official docs and what we saw differ on detail: the sharp install page lists only "CPU with SSE4.2" for Linux x64 and does not mention x86-64-v2 or POPCNT, while the error text above names v2. We check the whole v2 set to be safe. The error text was seen; whether sharp enforces every v2 flag was not tested.

The rpm loads the SELinux module `wazuh` (`semodule -i /var/ossec/var/selinux/wazuh.pp`) and removes it on uninstall. ✅ verified 2026-11-27 (Ubuntu 22.04 arm64 container, Rocky 9 arm64 rpm); the SELinux module is 👁 read from `rpm -qp --scripts`.
- The `.deb` carries a clearsigned dpkg-sig member `_gpgbuilder`: `gpg --verify _gpgbuilder` works directly, and the md5/sha1 inside match the members. `rpm -K` says `digests signatures OK` with only the Wazuh key imported. ✅ verified 2026-11-27.
- Wazuh security advisories are at `repos/wazuh/wazuh/security-advisories` on the GitHub API; the global `/advisories/GHSA-…` call gives 404 for them. ✅ verified 2026-11-27.
- The event channel on 1514 is AES with the agent key, not TLS (`crypto_method aes`, log line `Using AES as encryption method`). Whether it is FIPS-validated has not been checked. ✅ verified 2026-11-27 for the method; FIPS not checked.
